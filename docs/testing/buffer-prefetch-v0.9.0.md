# v0.9.0 시작 지연 및 구간별 준비 대기 개선

## 구현

기존 방식은 자막 없는 영상의 원음을 25초간 재생·녹음한 다음 원래 위치로 돌아왔다. 매 구간마다 같은 대기가 반복됐다.

새 방식은 YouTube가 현재 영상의 MediaSource에 전달한 오디오 바이트를 document_start에서 관찰한다. 추가 다운로드 요청, 로그인 쿠키, 마이크/탭 오디오를 사용하지 않는다. 원본 appendBuffer 입력과 반환/예외를 유지하고, 광고 및 현재 미디어와 연결되지 않은 버퍼는 사용하지 않는다. WebM/fragmented MP4 초기화 헤더와 최근 미디어를 최대 8 MiB로 보관하며 가능한 컨테이너 경계에서 오래된 데이터를 제거한다.

로컬 백엔드는 최대 26초 요청 구간만 ffmpeg로 잘라 Whisper에 전달한다. 네트워크 프로토콜을 허용하지 않고 요청 출처·파일 매직·길이·크기·동시 처리 수를 검사한다. 짧게 잘리거나 누락된 오디오는 유효한 자막 범위로 등록하지 않는다. 임시 원음은 처리 후 삭제한다.

첫 12초 원문에서 최대 세 문장을 준비하고 시작한다. 이후 다음 24초 분량을 앞서 인식하며, 음성 생성에 CPU가 필요하고 원문이 충분하면 추가 인식을 늦춘다. 번역과 음성은 두 문장씩 묶되, 음성 한 문장이 완성되면 NDJSON으로 해당 문서에 즉시 전달한다. 마지막 문장 완성을 기다려 이미 만든 음성을 막지 않는다. 요청 ID·문서 ID·세션 검사를 적용하며 Stop 뒤 도착한 결과는 버린다.

빠른 경로를 지원하지 않으면 기존 원본 재생 수집으로 복구하되 수집 길이를 8초로 줄인다. 이 경로에는 여전히 구간별 대기가 있다.

## Mac 처리 설정

- Mac 신규 설치 기본 STT는 Whisper base CPU int8. 버퍼 경로는 beam/best_of 1로 인식한다. 기존 일반 전처리 설정은 유지한다.
- 이 Mac도 base 모델을 다운로드해 적용했다. 기존 설치의 설정 파일은 설치 스크립트가 덮어쓰지 않으므로, 다른 기존 Mac은 모델 설치와 `YLD_STT_MODEL=base` 설정이 별도로 필요하다. small 모델을 유지하면 인식 정확도와 처리량의 균형이 달라진다.
- Mac Supertonic 작업 스레드 기본 2. 새 버퍼 경로는 5단계 합성, 다른 경로는 기존 8단계. 음성 캐시에 합성 단계 값을 포함한다. 음성 생성 속도 1.15는 유지한다.
- 동일 한국어 문장 실측: 4스레드/8단계 2.33초, 2스레드/8단계 1.76초, 2스레드/5단계 1.02초. 이 결과는 해당 Mac의 짧은 문장 측정이며 일반적인 성능 보장은 아니다.

## 검증 조건

2026-11-10, 기존 Mac Chrome의 https://www.youtube.com/watch?v=NL65Awuv8gU 탭. 각 모드를 50초부터 시작하고 여러 준비 구간을 지나 재생한다. 새 탭은 만들지 않았다. API 키는 기존 패널 저장 키를 사용한다. 영상·원문·번역·오디오 상태와 준비 대기 지표를 실제 페이지에서 관찰한다.

반복 측정이므로 원본 영상 버퍼와 번역/음성 캐시가 사용될 수 있다. 수치는 모델과 영상이 준비된 실행 결과이며, 캐시가 전혀 없는 새 영상의 첫 실행 수치로 일반화하지 않는다. 문장 끝을 자르지 않기 위한 짧은 영상 대기와 원문/TTS 준비 대기를 구분한다.

| 모드 | 첫 더빙 | 실제 재생 구간 | 준비 대기 | 문장 끝 보존 대기 |
| --- | --- | --- | --- | --- |
| 1. Gemma → Supertonic | 5.40초 | 50–128.37초 | 0회 / 0초 | 1회 |
| 2. Gemma → GPT 음성 | 8.88초 | 50–127.00초 | 0회 / 0초 | 0회 |
| 3. GPT 번역 → Supertonic | 12.82초 | 50–129.62초 | 0회 / 0초 | 2회 |
| 4. GPT 번역 → GPT 음성 | 8.43초 | 50–150.51초 | 0회 / 0초 | 1회 |

이전 v0.8.9는 같은 영상 구간에서 첫 더빙 38.76–42.36초였고 다음 구간마다 원음 수집 때문에 되감기/준비를 반복했다. 개선 후 첫 원문을 원래 위치에서 바로 인식하고 재생 중 다음 구간을 준비했다. 자동 음색 선택은 기존 설정 그대로이며, 원본 음색 판별이 불가능해 M1/marin 기본 음색이 사용됐다.

최적화 중간 단계에서는 로컬 모드에 CPU 경합과 묶음 완료 대기가 관측됐다. base STT, Mac 2스레드/5단계 합성, 초기 세 문장 확보, 이후 두 문장 묶음 및 문장별 즉시 전달을 적용한 뒤 위 결과를 측정했다. 일반 실행의 캐시를 삭제하지 않았으므로 콜드 캐시 벤치마크는 아니다. 4번에서 150.51초의 영상과 5.27/5.75초의 더빙이 함께 일시정지되는 것도 확인했다.

`npm run test:cloud`: 변경 전 141개, 최종 150개 통과. 버퍼 크기/컨테이너 헤더 보존, native append 반환·예외 유지, 다른 영상·광고 거부, ffmpeg 구간 자르기와 불완전 오디오 거부, 재생 중 선행 처리, Stop 뒤 결과 폐기, 문서별 스트림 전달·부분 프레임·오류 및 중복 오디오 방지 검사를 포함한다. Mock 회귀 검사와 위 실제 브라우저 검증은 별개다. `git diff --check` 통과.

한계: 모든 영상·네트워크·기기에서 무중단을 보장하지 않는다. 지원하지 않는 미디어 경로에는 8초 실시간 수집 대기가 남으며, 준비 속도가 재생을 따라가지 못하면 영상이 기다린다. 빠른 base 인식/5단계 합성은 small/8단계와 정확도·음질 차이가 있을 수 있다. Windows/Linux의 실제 재생 및 긴 영상의 8 MiB 롤링 경계 실기는 이번에 검증하지 않았다. 롤링 경계는 회귀 테스트로 확인했다.
